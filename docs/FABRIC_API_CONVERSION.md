# Fabric API -> NeoForge conversion (done, NOT compiled or run)

Written against the NeoForge 1.21.1 source (neoforged/NeoForge, branch 1.21.1): BakedModelWrapper,
ModelEvent.ModifyBakingResult / RegisterGeometryLoaders, IUnbakedGeometry / IGeometryLoader, ModelData /
ModelProperty, IBlockEntityExtension, and the 6-argument BakedQuad constructor were all checked there.

## What the old code did
- `DuplicateDownBakedModel` (Fabric `ForwardingBakedModel`): draws a block's model once normally and once more,
  moved down one block (all faces except DOWN, slightly squeezed). Used by blocks annotated
  `@SpecialOffset(DUPLICATE_DOWN)` when the state has `offset_toggle=true` or `extension_toggle=true`.
- `LoomBakedModel` (Fabric renderer transforms): draws the loom's "weave" model with its texture swapped to the
  sprite for the loom's current product (read from the BlockEntity), plus the "threaded" model on top.
- `TranslatedModelLoaderMixin`: hooked ModelBakery.putModel to swap these models in, with a ~400-line table for
  loom size / position / facing.
- `DependencyType`: FabricLoader.isModLoaded.

## What replaces it
| Old | New |
|---|---|
| DuplicateDownBakedModel (Fabric) | `DuplicateDownBakedModel extends BakedModelWrapper`, copies quads and shifts vertices (cached) |
| LoomBakedModel (Fabric) | `LoomBakedModel extends BakedModelWrapper`; re-maps UVs per quad; product comes via `ModelData` |
| Block entity lookup in the model | `LoomBlockEntity.getModelData()` + `requestModelDataUpdate()` |
| LoomUnbakedModel + mixin table | `LoomGeometry` (IUnbakedGeometry) + JSON models with `"loader":"conquest:loom"` |
| ModelBakery mixin for DUPLICATE_DOWN | `ConquestModelEvents.wrapDuplicateDown` on `ModelEvent.ModifyBakingResult` |
| Loom rotation/offset table | generated by `tools/gen_loom_models.py` into blockstates + `models/block/looms/dynamic/` |
| FabricLoader.isModLoaded | `ModList.get().isLoaded` |

`tools/setup_resources.sh` runs the generator. It rewrites the 4 loom blockstates so each old variant becomes
two: `...,has_thread=true` (new loader model, same `y` rotation) and `...,has_thread=false` (original model).
Result: 4 blockstates, 48 generated loom models; the generator checked that every referenced model exists in the jar.

## Things to verify when it first runs (these are my assumptions)
1. The generator copies the decision table from the mixin: medium/small shift 0.5, large shift 0.9, position 2 uses `_45` models.
2. Translation is applied in model space and then rotated (as the old `LoomTranslationBakeSettings` did) - check an
   east/west-facing loom at positions 3 and 4 is shifted the right way.
3. Blockstate keys with partial properties plus an added `has_thread=...` must still match exactly one variant per state.
4. `LoomBlockEntity.load/save` still use 1.20.1 method names; they must be ported to `loadAdditional(tag, registries)` /
   `saveAdditional(tag, registries)` and keep the `refreshModel()` call. Also check the client re-renders the loom when
   the product changes (may need `level.sendBlockUpdated`).
5. Vertex layout assumed: 8 ints per vertex, x/y/z at 0-2 and u/v at 4-5 (vanilla BLOCK format). Shader mods such as
   Iris/Embeddium use the same quads, so check the loom and DUPLICATE_DOWN blocks with shaders on.
6. `ModelEvent.ModifyBakingResult` map entries must be settable (`entry.setValue`). If it throws, collect into a new map and `putAll`.
7. `ModelResourceLocation.variant()` / `.id()` accessors and `ResourceLocation.parse/fromNamespaceAndPath` are 1.21 names.
8. If any of the 11 other mixins also touch model code, they conflict with none of this, but re-check them.
